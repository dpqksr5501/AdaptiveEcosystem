# 이주 이력을 다음 지역 생성에 반영하는 확장 계획

> 상태: 설계안. 코드·에셋 변경 전 검토용. 기존 M3.1~M3.3의 완료 선언이나 새 마일스톤 번호가 아니다.
>
> 기준: UE 5.8, Server/Standalone 권위, Mass Entity 단일 논리 개체, 지역별 정기 생성. 이번 요청에서는 코드를 변경하지 않는다.

## 1. 사용자 의도와 로그 판정

사용자가 원하는 결과는 **이주한 개체를 출발 지역에 복제하는 것**이 아니라, 이주가 출발지와 도착지에 남긴 환경·개체 정보를 각각 보관했다가 **양쪽 지역의 다음 적격 생성 웨이브에서 새 ID로 태어나는 개체의 초기 특성에 반영하는 것**이다. 이주한 개체는 도착 지역에 같은 StableAgentId로 남는다. 생성과 이주는 서로 다른 사건으로 장부와 표시에서도 구분한다. 도착지는 이주자가 겪은 출발지의 압력과 특성을 전달받되, 출발지의 Food/위협을 도착지의 현재 환경값으로 덮어쓰지 않는다.

첨부 로그의 첫 PIE는 Listen Server+Client였고 Client 콘솔의 `Debug.Starvation.Forest_A`는 권위 World가 없어 거절됐다. 두 번째 Standalone PIE에서는 A Food가 50→0(`ActualLoss=50`), ID 1~8이 시각 11초에 Traveling, 25~27.5초에 B 도착으로 기록됐다. 40초 일일 집계 A=0/B=16/총 16이다. **당시 빌드에는** `Manual Migration Test` 우회 설정이 있었고 `[Eco M3.2] Waves=0`에 따라 추가 생성은 한 번도 예약되지 않았다. 이후 이 우회 설정은 제거되었으며 현재 `Debug.Starvation` 명령은 Spawn Waves 설정을 변경하지 않는다. `mass.debug.DrawAllEntities`는 Transform Fragment가 있는 기존 Entity의 위치를 그리는 엔진 CVar이며 생성 명령이 아니다. 로그상 이 CVar 입력은 첫 PIE에서만 보이므로 두 번째 PIE의 실제 표시 상태는 로그만으로 단정할 수 없다. 시작 시 Windows의 profiler DLL 로드 실패는 이주 실패의 증거가 아니며, 이 로그에는 시뮬레이션 오류/크래시가 없다. 이 결과는 Standalone 이동과 집계의 확인이지, Client Bubble 표시 검증은 아니다.

현재 기본 자원 규칙은 `Food=0`인 지역의 추가 생성을 막고, 이번 M3 경로는 Food를 재생하지 않는다. 따라서 **A가 고갈된 채라면 다음 웨이브가 도래해도 A에서 새 개체가 태어나지 않는다.** 이주 이력은 보존하되, Food가 회복된 뒤 처음 도래하는 적격 웨이브에 반영한다. 고갈을 무시하는 강제 생성, 이동 개체의 복제, 놓친 웨이브의 일괄 보상은 기본 설계에 넣지 않는다.

## 2. 관찰 가능한 목표

1. Starvation, 플레이어 사냥 압력 등 원인별로 **실제로 완료된** 지역 간 이주를 기록한다. 취소·목적지 고갈로 대기·동일 지역 복귀는 성공 이주로 집계하지 않는다.
2. 한 번의 완료 이주로 출발 지역/종의 **유출 이력**과 도착 지역/종의 **유입 이력**을 각각 한 번 갱신한다. 원인, 출발 당시 Food/위협, 이주자 특성, 도착 당시 지역 환경을 구분해 저비용으로 보관한다. 새 개체의 주인이나 Population 진실값은 이 기록에 저장하지 않는다.
3. 다음 **자원·상한 조건을 만족하는 정규 생성 웨이브**가 어느 지역에 오든, 그 지역의 현재 환경·거주 개체 요약과 유출/유입 이력을 함께 사용해 해당 웨이브의 새 개체에게 고정된 지역 적응 프로필을 적용한다. 기존 주민·이주자·도착지 개체의 특성을 소급 변경하지 않는다.
4. 새 개체의 StableAgentId는 반드시 새로 발급한다. 전체 Alive 수 변화는 성공한 신규 생성 수와 실제 사망 수로만 설명한다. 이주만으로 전체 Alive는 변하지 않는다.
5. 로그와 디버그 표시에서 `Moved(ID 유지)`와 `Born(ID 신규, BirthRegion/ProfileRevision/영향 출처 표시)`를 분리해 확인한다.

### 이주 원인과 기록 시점

- 원인은 `FoodDepletion`, `PlayerThreat`, 향후 `PredatorThreat`, `Other`처럼 명시적 분류로 시작한다. 한 이동에 복수 압력이 있으면 **결정 시점의 원인 snapshot**과 우선순위로 대표 원인 하나를 고정하고 보조 원인은 비트/값으로 남긴다. 도착 당시 Food 상태만 보고 원인을 다시 추정하지 않는다.
- 출발 때 Mass Travel 상태에 원인·환경값을 보관하고, **서로 다른 Region으로 도착 commit**할 때만 `MigrationOutcome`을 한 번 발행한다. 기준 key는 `(WorldEpoch, StableAgentId, 출발 commit 일련번호)`로 하여 재처리·Late Join·PIE 재시작에서 중복 반영하지 않는다. 이 결과 한 건을 Ecology가 검증하고 같은 단계에서 출발지의 유출 집계와 도착지의 유입 집계를 함께 갱신한다. 둘 중 하나만 기록하거나 두 지역에 별개의 성공 이주를 만든 것으로 세지 않는다. 현재 인구 집계는 기존 Mass query 결과만 사용한다.
- 실제 Bootstrap 인스턴스는 이주 사건의 소유자가 아니다. 지역·종별 이력은 권위 World의 Ecology에 하나만 두고, 해당 지역·종을 생성하는 모든 Bootstrap은 요청에 실린 **동일 Revision의 읽기 전용 출생 프로필**을 소비한다. Bootstrap의 수/재생성/호출 순서가 이주 집계를 바꾸어서는 안 된다.
- 사용자가 말한 플레이어 사냥에 의한 도망은 아직 이 M3 Box 경로의 권위 이주 입력이 아니다. 추후 서버의 피해/사냥/위협 사건을 `RegionId`와 `StableAgentId`로 검증해 압력 snapshot으로 전달한 뒤, **실제 이주가 일어난 경우에만** 이주 이력으로 기록한다. 사망 사건은 기존 `PredationHistory`와 사망 처리에 별도로 반영한다. 좌표 기반 `UEcoRegionPredationSubsystem` 값을 RegionId 기반 자원 상태에 무심코 합치지 않는다.

### 어떤 ‘특성’을 반영할지

첫 단계는 현재 Shared PPO 모델의 7→64→64→4 가중치를 바꾸지 않고 개체마다 보관할 수 있는 좁은 초기값으로 제한한다. 예를 들어 정규화된 `MigrationSensitivity`와 `ThreatSensitivity`를 새 Mass 개체 Fragment에 둔다. 각 값은 종 기본값, **생성 지역의 현재 환경·생존 주민 요약**, 최근 유출 압력, 유입 개체의 특성·경험에서 설정 가능한 작은 가중치로 합성하고 허용 범위로 clamp한다. `FoodDepletion` 때문에 A에서 온 개체의 경험은 B의 유입 압력이지 B의 식량 고갈 사건이 아니다. Starvation이 많았다는 사실만으로 모든 신규 개체가 반드시 이주하거나 생존 능력이 유전적으로 좋아졌다고 간주하지 않는다.

현재 정기 생성은 부모를 선택하지 않으므로 이것은 **지역 환경에 따른 출생 초기화**다. 진짜 유전·혈통을 원하면 추후 생존한 부모의 StableAgentId와 자손 관계, 교배/선택 규칙을 별도 설계해야 한다. 기존 `Evolution/`의 LLM Proposal/Generation Profile을 새 경로로 재사용하지 않는다. Trait가 실제 이주 임계값·위협 회피·속도에 영향을 주는 단계에서는 Starvation의 기본 생존 규칙을 유지하면서 Python 시뮬레이터와 C++ 정책/조향의 의미를 함께 갱신한다. PPO 7개 관측이나 4개 행동 계약을 바꾸면 정책 계약 버전과 파리티 검증도 변경한다.

## 4. 다음 생성 주기 적용 규칙

1. 지역별 기존 Day/Night 웨이브 시간·기본 수량을 유지한다. 예약 전에 현재 Food>0, 종/지역 제한, 전체 128 상한과 기존 예약 수를 확인한다. 생성 가능 수는 기존 웨이브 수량과 지역/전체 잔여 수용량의 최솟값이다. 도착 지역의 이주 유입은 그 지역의 현재 Mass Population으로 이미 계산되므로 새 생성 수를 늘리지 않으며, 상한에 가까우면 실제 생성 수를 줄인다. 유입만으로 즉시 생성하거나 보충 웨이브를 열지 않는다.
2. 자격이 되는 웨이브가 생성 요청을 만들 때 Ecology가 해당 지역·종의 **현재 로컬 환경 + 유출/유입 이력**으로 `BirthProfile`을 계산하고 `ProfileRevision`과 특성 snapshot을 고정한다. 이후 같은 요청을 처리하는 동안 새 이주 결과가 도착해도 이미 확정된 출생 특성은 바뀌지 않는다. 한 웨이브에 여러 Bootstrap이 참여하면 같은 지역·종·웨이브에 같은 프로필을 공유한다.
3. 같은 Step에 `환경 이벤트 → 스폰 → 이주 도착`이 겹치면 기존 처리 순서상 해당 웨이브에는 **이전 Step까지 완료된 이력만** 적용한다. 방금 도착한 이주는 그다음 웨이브에 반영한다. 요청/결과·이력 갱신은 GameThread의 단계 경계에서 수행한다.
4. 웨이브가 Food=0 또는 상한 때문에 0마리면 기존처럼 `Spawn Skipped`로 종료한다. 유출/유입 이력은 소진하지 않고 시간 기준 감쇠 규칙에 따라 유지한다. 조건이 다시 충족된 뒤의 **다음 예정 웨이브**가 사용한다. 별도 누적 결손 수나 이주자 수만큼의 강제 보충은 만들지 않는다.
5. 실제 생성 수만큼 새 ID를 발급하고 개체별 Fragment의 특성값을 초기화한다. 부모/원본 이주 ID를 새 Entity의 Identity로 복사하지 않는다. Debug에는 `BirthRegion`, `ProfileRevision`, 로컬/유출/유입 영향값과 새 ID를 기록한다.

### 도착지 경험과 원래 생성 규칙의 결합

한 지역·종의 `BirthProfile`은 **종 기본값 → 그 지역의 현재 Food/PredationHistory·환경·생존 주민 요약 → 최근 유출 이력 → 최근 유입 이력** 순서로 계산한다. 유출과 유입은 각각 별도 채널이므로 B에 도착한 A의 `FoodDepletion`은 B의 `FoodAmount=0`이나 B의 로컬 `PredationHistory`로 환산하지 않는다. 유입 집계에는 원인별 건수, 출발 압력, 도착 시 B의 환경 snapshot, 이주 개체의 특성 평균/분산, 마지막 도착 시각을 둔다. B가 다시 C로 이주시킨 경우 B→C의 새 완료 사건으로 기록하되 A→B의 경험을 매번 원본 사건처럼 재전파하지 않는다.

초기 합성 규칙은 결정적이고 제한적이어야 한다. `BaseTrait`에서 시작해 로컬 환경/주민 보정, 유출 압력 보정, 유입 특성·원인 보정을 더한 뒤 종별 허용 범위로 clamp한다. 각 보정의 부호와 최대 크기는 종별 설정값으로 명시하고, 유입의 유효 가중치는 `min(MaxIncomingWeight, RecentArrivals / max(1, CurrentResidents + RecentArrivals))`로 상한을 둔다. 유출도 별도의 `MaxOutgoingWeight`로 제한한다. 최근 도착 1마리가 큰 지역의 다음 세대를 지배하지 않게 최소 표본 수 또는 낮은 신뢰도 가중치를 적용한다. 주민이 0명이어도 종 기본값을 유지하고 유입 영향은 설정된 상한까지만 허용한다. 시간 감쇠와 같은 입력 순서에서 같은 프로필이 나오도록 집계·반올림 순서를 고정한다. 구체적인 기본 가중치와 특성별 부호는 구현 전 종별 설계값으로 확정하고 에디터에서 조정 가능하게 둔다.

이 계획에서 이주 이력은 **출생 특성**을 조정한다. 생성 시각·기본 수량은 기존 Spawn Schedule이 정하며, 도착 개체가 차지한 Population과 도착지의 현재 Food/상한이 실제 생성 가능 수를 결정한다. 유입이 출산율을 직접 올리는 규칙은 넣지 않는다. 필요해지면 생존/사망·자원 소비와 함께 검증할 별도 정책으로 추가한다. `Debug.Starvation.<RegionId>`는 해당 지역 Food 사건만 만들며 Spawn Schedule이나 프로필 가중치를 바꾸지 않는다.

이주 이력의 메모리는 지역/종별 고정 크기 **유출·유입 집계**(감쇠 압력, 횟수, 특성 평균/분산, 마지막 Step/시각)를 기본으로 한다. 전체 Agent의 이벤트를 무한히 쌓지 않는다. 상세 ID 추적과 중복 방지 키는 제한된 진단/수신 기록으로 관리하고, 세션 간 영속화가 필요해지면 버전 있는 SaveGame 계약을 별도로 정한다. `RegionId`/`SpeciesId`는 장기 key, compact index는 현재 World의 Mass hot path에서만 사용한다. Event 압력의 감쇠는 시간 기반으로 정의해 웨이브 스킵이나 FPS에 의해 결과가 달라지지 않게 한다.

## 5. 구현 순서와 완료 판단

| 단계 | 작업 | 수동 확인 기준 |
| --- | --- | --- |
| A. 기준선/표시 진단 | 이전 첨부 로그는 Waves=0 상태의 생성 16·도착 후 16으로 기록한다. 현재 빌드에서는 Waves=true로 두고 같은 PIE에서 주기 생성과 이주를 함께 확인한다. `mass.debug.DrawAllEntities`는 권위 게임 뷰포트에서 켜고, 생성과 표시를 분리해 관찰 | 기존 이주 ID는 유지되고 Food=0인 A만 웨이브가 스킵되며 B는 계속 생성 |
| B. 원인·결과 계약 | 원인·출발 특성 snapshot, 도착 시 단발 `MigrationOutcome`, 취소/대기 처리, RegionId·SpeciesId 귀속, 중복 방지 | Starvation A→B 8건: A 유출 8, B 유입 8, B 유출 0. 전체 성공 이주는 8건 |
| C. 양방향 지역 적응 이력 | Ecology에 지역·종별 유출/유입 집계와 감쇠/Revision을 추가하고 완료 경계에 함께 게시. 도착 시 목적지 환경 snapshot을 연결하되 현재 Population/자원 소유권과 분리 | A 유출 8/B 유입 8, 전체 Alive 16, 양쪽 Food 장부 불변. PIE 재시작 시 이력 초기화 |
| D. 정규 웨이브의 새 개체 | 요청 시 로컬 환경·유출·유입 프로필 snapshot 확정, Bootstrap이 개체별 Trait와 신규 ID 초기화, 성공 수만 집계 | B의 다음 적격 웨이브가 A 이주자 유입 영향을 사용. A는 Food=0이면 스킵. 원래 웨이브 수량·시간·상한 준수 |
| E. 위협 입력 확장 | 서버 플레이어 피해/사냥 압력을 RegionId 기준으로 수집하고 실제 이주 원인으로 연결. 이후 포식자·날씨 원인을 같은 계약에 추가 | 사냥으로 도망만 친 개체와 실제 타 지역 도착을 구분, 사망은 별도 기록 |
| F. 특성의 실제 행동 효과 | 작은 per-agent 특성이 이동/위협 판단에 미치는 한계를 정하고 Python/C++ 계약을 함께 갱신 | 같은 입력·특성에 Python/Unreal 결과 일치, Starvation 시 기본 탈출 규칙 유지 |

에디터 시나리오는 두 개로 나눈다. **위협 기반:** A/B Food>0, Spawn Waves=true. 서버 위협으로 A→B 이주를 완료한 뒤 양쪽 다음 예정 웨이브에서 각각 A의 유출 영향과 B의 유입 영향이 있는 새 ID·ProfileRevision을 확인한다. **기아 기반:** 현재처럼 A를 0으로 만든 뒤 A의 웨이브는 스킵되지만 B의 웨이브는 계속되어야 한다. B의 다음 적격 웨이브에는 A에서 온 개체의 원인·특성이 반영되어야 하며 B 자신의 Food는 그대로 양수여야 한다. 이후 Food 회복 기능 또는 테스트 전용 권위 자원 이벤트를 **기존 Ecology 자원 장부 경로**에 추가하고 A Food를 양수로 복구한 후 다음 예정 웨이브에서 A의 유출 영향도 확인한다. B가 이주 도착으로 지역 상한에 도달한 경우에는 B의 신규 생성은 0이고 유입 이력만 남는다. 자원 회복 없이 A 생성까지 요구하면 기존 `Food=0 → Spawn=0` 계약을 먼저 바꾸는 별도 생태 규칙 결정이 필요하다.

최종 불변식은 `전체 Alive = 초기 생성 + 성공 웨이브 생성 - 실제 사망`, `전체 Alive = 모든 Region Population 합`, `이주 완료 자체의 Alive 변화=0`, `각 완료 이주 outcome의 출발지 유출 반영=1회·도착지 유입 반영=1회`, `신규 개체 ID ≠ 이주 개체 ID`, `0 Food 지역 신규 생성=0`, `프로필 영향은 완료 이후의 적격 웨이브부터`이다. Listen Server/Client에서는 Client의 Bubble 가시 개수를 전체 Population으로 검증하지 않고, 현재 완료 요약과 관련 Box의 ID/Transform/Region만 비교한다. 구현 후 AGENTS.md에 따라 UE 5.8 Editor UBT 빌드와 수동 PIE를 수행한다. 이번 설계 단계에서는 수행하지 않는다.
