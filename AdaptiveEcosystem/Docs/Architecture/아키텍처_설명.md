# 1. 프로젝트가 해결하려는 문제

AdaptiveEcosystem의 핵심 목표는 단순히 몬스터 AI를 만드는 것이 아니다.

플레이어의 행동과 월드 환경 변화가 장기적으로 누적되고, 그 결과가 지역별 몬스터 종의 특성에 반영되는 **동적 생태계 시스템**을 만드는 것이 목적이다.

예를 들어:

```text
Forest_A 지역에서
플레이어가 Wolf를 지속적으로 사냥함
        ↓
Hunting / Pursuit / Threat Pressure 증가
        ↓
Evolution System이 현재 환경과 종 상태를 분석
        ↓
Wolf의 다음 세대 Trait 변화 제안
        ↓
검증 후 Species Profile 갱신
        ↓
이후 Spawn되는 Wolf가
더 작고 / 빠르고 / 겁이 많게 표현됨
```

중요한 점은 **현재 살아 있는 몬스터 한 마리가 갑자기 진화하는 것이 아니라**, 장기적인 생태 상태가 다음 세대 또는 이후 Spawn되는 개체에 반영된다는 것이다.

# 3. 가장 중요한 설계 원칙

## 3.1 Server가 최종 Authority다

생태계는 장기 상태를 가진다.

예:

```text
Population
Player Pressure
Generation
Species Profile
Migration
Resource
Risk
Energy
```

이 값이 Client마다 다르면 월드 자체가 서로 다른 상태가 된다.

따라서 다음 정보는 Server가 최종 결정한다.

```text
Server
├─ Ecology State
├─ Player Pressure
├─ Population
├─ Evolution Profile
├─ Generation
├─ Migration
├─ Mass Logical State
└─ AI Proposal 최종 승인
```

Client는 **결정된 결과를 받아 표현하는 역할**을 한다.

### 왜 이렇게 했는가?

멀티플레이 환경에서:

```text
Client A : Wolf Fear = 0.8
Client B : Wolf Fear = 0.3
Server   : Wolf Fear = 0.5
```

같은 상황이 생기면 안 되기 때문이다.

따라서:

> **판단은 Server, 표현은 Client**

를 기본 원칙으로 둔다.

# 4. 왜 `Region × Species`가 핵심 단위인가?

진화 상태를 전역 Species 하나로 관리하면:

```text
Wolf = Fear 0.8
```

밖에 표현할 수 없다.

하지만 우리가 원하는 것은:

```text
Forest_A / Wolf
Forest_B / Wolf
Desert_A / Wolf
```

가 서로 다른 환경과 플레이어 압력을 받는 것이다.

따라서 핵심 상태 단위는:

```text
RegionId + SpeciesId
```

이다.

예:

```text
Forest_A × Wolf
Population = 83
Fear = 0.81
Aggression = 0.22

Forest_B × Wolf
Population = 141
Fear = 0.34
Aggression = 0.71
```

이 구조를 사용하면 같은 종이라도 지역에 따라 다른 생태적 특성을 가질 수 있다.

### 현재 ID

```cpp
FName RegionId;
FName SpeciesId;
```

초기에는 단순한 `FName`으로 시작한다.

향후 필요하면 Strong ID Wrapper나 별도 Key 구조체로 변경해도 된다.

# 5. 왜 Trait을 그룹으로 나누었는가?

현재 Trait은 대략 다음 네 영역으로 나뉜다.

```text
Phenotype
Gameplay
Behavior
Ecology
```

## Phenotype

몬스터의 외형적 표현.

```text
BodyScale
LegScale
BodyBoneScale
ColorBrightness
ColorTintStrength
MorphWeight
```

## Gameplay

게임플레이 수치.

```text
MoveSpeedMultiplier
HealthMultiplier
AttackMultiplier
```

## Behavior

개체의 행동 성향.

```text
Fear
Aggression
GroupAffinity
HidePreference
```

## Ecology

장기 생태 행동.

```text
MigrationTendency
RoamRadiusMultiplier
DayActivityPreference
NightActivityPreference
```

### 왜 그룹을 나누었는가?

Trait이 20~30개가 되었을 때 하나의 거대한 구조체에 전부 넣으면:

```text
어떤 값이 외형인지
어떤 값이 AI인지
어떤 값이 Population 시스템에서 쓰이는지
```

구분하기 어려워진다.

또한 각 담당자가 자신의 영역만 사용할 수 있게 된다.

```text
Creature Morphology → Phenotype
Combat/Movement    → Gameplay
Utility AI         → Behavior
Ecology Runtime    → Ecology
```

# 6. 왜 LLM이 직접 Actor를 바꾸지 않는가?

프로젝트에서 LLM의 역할은 중요하지만, LLM은 **권한을 가진 게임 시스템이 아니다.**

잘못된 구조:

```text
LLM
 ↓
Wolf Actor 찾기
 ↓
SetActorScale()
 ↓
MoveSpeed 변경
```

이 방식은 다음 문제가 있다.

```text
재현성 부족
멀티플레이 Authority 문제
잘못된 값 방어 어려움
LLM 실패가 Gameplay 실패로 연결
디버깅 어려움
Save/Load 어려움
```

그래서 현재 구조는:

```text
FEvolutionContext
        ↓
LLM
        ↓
FEvolutionProposal
        ↓
Validator
        ↓
FSpeciesEvolutionProfile
        ↓
Creature
```

이다.

즉:

> **LLM은 제안하고, Server가 검증하고, 게임 시스템이 적용한다.**

# 7. 왜 LLM이 Trait 값을 직접 제안하는가?

초기 아이디어 중 하나는:

```text
LLM
 ↓
"Evasive"
 ↓
개발자가 미리 정한 Evasive 수치 적용
```

같은 방식이었다.

하지만 이 방식은 사실상 LLM이 단순한 Classifier 역할만 하게 된다.

현재 프로젝트에서는 LLM이 허용된 Trait 공간 안에서 실제 Delta를 제안하도록 한다.

예:

```json
{
  "body_scale_delta": -0.03,
  "move_speed_delta": 0.04,
  "fear_delta": 0.07,
  "aggression_delta": -0.05
}
```

다만 LLM이 모든 값을 자유롭게 결정하는 것은 아니다.

Validator가:

```text
Hard Min / Max
Max Delta Per Generation
Mutation Budget
NaN / Inf
Revision
Stale Context
```

등을 검사한다.

# 8. 왜 `Proposal → Validator → Commit` 구조인가?

이 구조는 프로젝트에서 매우 중요한 경계다.

```text
AI Output
   ↓
Proposal
   ↓
Validation
   ↓
Commit
```

AI의 출력과 실제 게임 상태 사이에 **검증 단계**를 둔다.

예를 들어 LLM이:

```text
BodyScaleDelta = +4.0
FearDelta = NaN
```

을 반환해도 실제 게임 상태에 바로 반영되지 않는다.

현재 Validator는 다음을 담당한다.

```text
WorldEpoch 검사
ContextRevision 검사
NaN / Inf 검사
Trait별 Delta 제한
Mutation Budget
Trait Hard Limit
Generation 증가
ProfileRevision 증가
```

### Mutation Budget

한 세대에서 너무 많은 Trait이 동시에 크게 변하지 않도록 한다.

\[
\sum_i |\Delta Trait_i| \le B
\]

예를 들어:

```text
MutationBudget = 0.35
```

라면 전체 변화량의 합이 이를 넘지 않도록 조정한다.

# 9. 왜 `World`와 `Ecology`를 분리했는가?

World 담당 시스템의 질문은:

> **현재 이 지역의 환경은 어떤가?**

이다.

예:

```text
Temperature
Humidity
Rainfall
VegetationDensity
FoodAvailability
Day / Night
Shelter
Spawnable Area
```

Ecology의 질문은:

> **그 환경과 플레이어 행동 때문에 생태계가 어떻게 바뀌는가?**

이다.

예:

```text
Population 감소
Migration 증가
Fear 증가
Night Activity 증가
```

따라서:

```text
World
  ↓
Environment State
  ↓
Ecology
```

의 단방향 관계를 만든다.

World가 직접:

```text
비가 많이 옴 → Wolf Fear +0.1
```

같은 결정을 하지 않는다.

# 10. 왜 Creature가 EcologySubsystem을 직접 조회하지 않는가?

Creature는 **결정자**가 아니라 **표현자**다.

잘못된 구조:

```text
ACreatureCharacter
      ↓
EcologyServerSubsystem 찾음
      ↓
Profile 직접 조회
```

이 구조에서는 Creature가 Server/Ecology 내부 구조를 알아야 한다.

나중에:

```text
Mass
Replication
Spawner
Save/Load
Pooling
```

이 들어오면 결합도가 급격하게 증가한다.

그래서 현재 구조는:

```text
Server / Spawner / Representation
            ↓
FCreatureSpawnData
FSpeciesEvolutionProfile
            ↓
ACreatureCharacter.InitializeCreature()
            ↓
UCreatureTraitComponent
```

이다.

Creature는:

```text
누가 Profile을 만들었는지
LLM이 무엇인지
Pressure가 무엇인지
Mass가 무엇인지
```

알 필요가 없다.

# 11. 왜 `FCreatureSpawnData`가 별도로 존재하는가?

Species Profile과 개체 정보는 서로 다르다.

Species Profile:

```text
Forest_A × Wolf 전체가 공유하는 특성
```

Spawn Data:

```text
현재 활성화되는 특정 개체의 식별 정보
```

예:

```text
FCreatureSpawnData
├─ StableAgentId
├─ WorldEpoch
├─ ControlEpoch
├─ RegionId
├─ SpeciesId
├─ Generation
├─ ProfileRevision
└─ RandomSeed
```

이를 분리하면 나중에 Mass Entity가 Actor Representation으로 전환될 때:

```text
Logical Agent
      ↓
SpawnData
      ↓
Actor
```

형태로 자연스럽게 연결할 수 있다.

# 12. 왜 `StableAgentId`가 필요한가?

MassEntity Handle이나 Actor Pointer는 영속적인 ID가 아니다.

예:

```text
Wolf #42
Mass Entity
    ↓ Near Player
Creature Actor 생성
    ↓ Far Away
Actor 제거
    ↓
Mass Entity 상태로 복귀
```

이 과정에서 같은 개체라는 것을 계속 추적해야 한다.

따라서:

```text
StableAgentId
```

를 사용한다.

다음 값들은 장기 ID로 사용하지 않는다.

```text
Actor Pointer
Mass Entity Handle
ISM Instance Index
Array Index
```

# 13. 왜 Mass와 Actor를 분리하려는가?

MMORPG 수준의 생태계를 생각하면 모든 몬스터를 항상 `ACharacter`로 유지하기 어렵다.

예:

```text
25,000 logical creatures
```

를 모두:

```text
ACharacter
SkeletalMesh
AnimBlueprint
AIController
Collision
Tick
```

으로 돌리는 것은 매우 비싸다.

그래서 장기적으로:

```text
Far / Unimportant
→ Mass Logical Simulation

Near / Important
→ Active Actor Representation
```

구조를 사용한다.

예:

```text
Mass Wolf #1932
HP = 64
Energy = 0.42
Region = Forest_A
Position = ...

          ↓ 플레이어 접근

ACreatureCharacter
StableAgentId = 1932
HP = 64
ProfileRevision = 17
```

Actor가 제거되어도 논리 개체는 사라지지 않는다.

# 14. 왜 Simulation Policy AI와 Evolution LLM을 분리했는가?

프로젝트에는 서로 다른 종류의 AI가 존재할 수 있다.

## Evolution LLM

질문:

> 환경과 플레이어 압력을 봤을 때 Species Trait이 어떻게 변해야 하는가?

입력:

```text
Environment
Pressure
Population
Current Profile
Generation
```

출력:

```text
Trait Delta
```

## Simulation Policy AI

질문:

> 현재 서버 부하에서 어떤 Simulation LOD / Budget 정책을 사용하는 것이 좋은가?

입력:

```text
Entity Count
Processor Cost
CPU Metric
Near/Mid/Far LOD Count
```

출력:

```text
Suggested Policy
```

둘은 목적도, 데이터도, 실패 시 영향도 다르다.

따라서 별개의 시스템으로 유지한다.

# 15. 왜 실제 LLM은 비동기로 처리해야 하는가?

실제 Local LLM 추론은 수 ms가 아니라 수십~수백 ms 이상 걸릴 수 있다.

Game Thread에서:

```cpp
RequestLLM();
Wait();
```

하면 게임 전체가 멈출 수 있다.

따라서 실제 LLM은:

```text
Game / Server Thread
        ↓
Context Snapshot
        ↓
Async Worker
        ↓
LLM Inference
        ↓
Result Queue
        ↓
Server
        ↓
Validator
        ↓
Commit
```

형태가 된다.

현재 `IEvolutionDecisionProvider`의 동기 호출은:

```text
Dummy
Rule-Based
Fallback
```

용으로 사용할 수 있다.

실제 LLM 구현을 이 함수 안에 blocking 방식으로 넣지 않는다.

# 16. 왜 Subsystem에서 Replication하지 않는가?

`UWorldSubsystem`은 게임 로직을 관리하기에는 좋지만 Replicated Actor가 아니다.

따라서:

```text
UEcologyServerSubsystem
```

은:

```text
Ecology 계산
Profile 저장
Pressure 관리
Evolution Commit
```

등을 담당할 수 있지만 직접 Replication Transport가 되지는 않는다.

Network는 나중에:

```text
GameState
또는
Replicated Actor
또는
Replicated Component
```

가 담당한다.

예:

```text
UEcologyServerSubsystem
        ↓
FReplicatedSpeciesState
        ↓
AEcologyStateReplicator / GameState
        ↓
Client
```

# 17. 왜 Species Profile을 모든 Creature에 반복 복제하지 않는가?

같은 지역의 Wolf 300마리가 모두 같은 Profile을 사용한다고 가정하면:

```text
Wolf #1 → 전체 Profile
Wolf #2 → 전체 Profile
Wolf #3 → 전체 Profile
...
Wolf #300 → 전체 Profile
```

을 반복해서 보낼 필요가 없다.

대신:

```text
Forest_A × Wolf
ProfileRevision = 17
```

Profile을 한 번 관리하고 개체는:

```text
RegionId
SpeciesId
ProfileRevision
StableAgentId
```

정도만 가진다.

이를 통해 Network와 메모리 비용을 줄일 수 있다.

# 18. 왜 처음부터 모든 기능을 만들지 않는가?

현재 프로젝트는 다음 기능을 장기적으로 포함할 수 있다.

하지만 처음부터 전부 연결하면 어느 부분이 잘못됐는지 알기 어렵다.

그래서 Vertical Slice 방식으로 개발한다.

```text

Debug Fear/Aggression
→ Utility AI
```

이 방식은 전체 구조를 유지하면서 각 기능을 독립적으로 개발할 수 있게 한다.

# 19. 왜 현재는 단일 Unreal Module인가?

현재 프로젝트는:

```text
AdaptiveEcosystem
```

단일 Runtime Module을 사용한다.

초기부터:

```text
WorldModule
EcologyModule
CreatureModule
LLMModule
NetworkModule
MassModule
```

처럼 나누면 Build Dependency와 Plugin 관리가 오히려 복잡해질 수 있다.

따라서 현재는:

```text
Source/AdaptiveEcosystem/
├─ Core/
├─ World/
├─ Ecology/
├─ Evolution/
├─ Creature/
├─ Network/
└─ Debug/
```

처럼 폴더 수준에서 경계를 유지한다.

### 언제 Module/Plugin으로 나눌 수 있는가?

다음 조건이 생기면 검토한다.

```text
Mass Runtime이 독립적으로 커짐
외부 LLM Runtime dependency가 커짐
다른 프로젝트에서도 재사용 필요
Build dependency 분리가 실제 이점이 있음
Server-only code 분리가 필요
```

즉:

> **지금 단일 Module인 것은 최종 결정이 아니라 현재 규모에 맞춘 선택이다.**

다음은 충분히 변경 가능하다.

```text

Trait 구성

Save Format
LLM Backend
Async Task 구현
Utility AI 계산 방식

Environment State 필드
```

예를 들어:

```text
UEcologyServerSubsystem
```

이 나중에 너무 커진다면:

```text

Evolution Service
Species State Repository
```

로 분리해도 된다.

# 21. 무엇은 쉽게 깨면 안 되는가?

구현은 바꿔도 되지만 다음 **의미적 경계**는 이유 없이 무너뜨리지 않는다.

## Server Authority

Client가 장기 Ecology 상태를 결정하면 안 된다.

## Proposal / Validation / Commit

AI 출력이 검증 없이 게임 상태를 직접 변경하면 안 된다.

## Creature Representation Boundary

Creature가 LLM, Pressure, Mass 내부 구조를 직접 알아서는 안 된다.

## World / Ecology Boundary

World가 Evolution 결과를 결정하거나 Ecology가 Level Actor를 무분별하게 직접 조작하는 구조는 피한다.

## Stable Identity

Actor나 Mass Handle을 장기 ID로 사용하지 않는다.

## Async LLM

실제 LLM 추론으로 Game Thread를 blocking하지 않는다.

```text
   어느 책임이 이동하는가?

4. 다른 팀원의 코드가 새로운 내부 구현을 알아야 하는가?

5. 공통 Data Contract가 바뀌는가?

6. Server Authority가 유지되는가?

7. AI 출력이 Validator를 우회하지 않는가?

8. Mass 내부 타입이 Creature/World에 새어나가지 않는가?
```

단순히:


만으로 핵심 경계를 바꾸지 않는다.

# 25. AI Coding Agent가 이 문서를 읽을 때

AI Agent는 이 문서를 **절대적인 구현 명세**가 아니라 **설계 의도와 변경 기준**으로 사용한다.

Agent는 다음 행동을 권장한다.

```text
현재 코드를 먼저 확인
        ↓
문서와 현재 코드 차이 확인
        ↓
문제를 정의
        ↓
최소 변경으로 해결
        ↓
Build/Test
        ↓
변경 이유 보고
```

Agent가 하지 말아야 할 행동:

```text
문서를 보고 대규모 Refactor 자동 수행
미래 기능을 임의로 전부 구현
새 Plugin/Module을 이유 없이 생성
공통 Contract를 조용히 변경
Server Authority를 Client로 이동
LLM에서 Actor 직접 수정
Mass Handle을 외부 ID로 노출
```

문서와 실제 코드가 충돌한다면:

> **현재 동작하는 코드를 우선 분석하고, 왜 충돌하는지 보고한 뒤 수정한다.**

# 26. 현재 구조가 완벽하지 않아도 되는 이유

이 프로젝트는 연구와 게임 구현이 함께 진행된다.

초기에는 모르는 것이 많다.

예:

```text
Mass를 실제로 몇 Entity까지 사용할지
LLM 추론 주기
Evolution Trigger 조건
Network Update 주기
Species Profile 개수

Utility AI 구조
```

따라서 현재 아키텍처는 모든 답을 미리 고정하기 위한 구조가 아니다.

대신:

```text
확실하지 않은 내부 구현
```

과

```text
팀 간 연결 Contract
```

를 분리하기 위한 구조다.

그래서 각 파트는 내부 구현을 바꾸면서도 다른 팀의 작업을 최대한 깨뜨리지 않을 수 있다.

# 27. 이 프로젝트에서 좋은 구조란?

좋은 구조는 클래스가 많거나 패턴을 많이 쓰는 구조가 아니다.

이 프로젝트에서는 다음 조건을 만족하면 좋은 구조다.

```text
각 담당자가 독립적으로 개발 가능하다.

LLM 없이도 게임이 실행된다.

Mass 없이도 Creature 테스트가 가능하다.

실제 Weather 없이도 Ecology 테스트가 가능하다.

Network 없이도 Server Logic 테스트가 가능하다.

AI가 실패해도 게임 상태가 망가지지 않는다.

어떤 값이 어디서 결정되었는지 추적할 수 있다.

새 기능이 기존 계층의 내부 구현을 과도하게 알 필요가 없다.
```

# 28. 현재 첫 번째 통합 목표

현재 팀의 첫 번째 중요한 Vertical Slice는 다음이다.

```text
World
└─ Forest_A

Server / Ecology
├─ Wolf Species Profile (Monster)
│  ├─ BodyScale = 0.90
│  ├─ MoveSpeedMultiplier = 1.10
│  ├─ Fear = 0.80
│  └─ Aggression = 0.20
│
└─ Grass_A Evolution Profile (Vegetation)
   ├─ GrowthRate = 1.00
   ├─ RegenerationRate = 1.00
   └─ GrazingResistance = 0.50

        ↓

Creature / Ecology Test Harness
├─ ACreatureCharacter.InitializeCreature(Wolf)
├─ AEcologyBootstrapTestActor.RunVegetationEvolutionTest(Grass_A)
└─ AEcologyBootstrapTestActor.RunEcosystemFeedbackLoopTest()

        ↓

실제 결과
├─ 몬스터 크기(0.90), 속도(1.10), Fear(0.80), Aggression(0.20) 런타임 외형/스탯 반영
├─ 초식 이벤트 발생(RecordGrazing) → 식생 밀도/먹이 가용성 감소 및 GrazingPressure 누적
├─ 식생 제안/검증/커밋 → 2세대 식생의 GrazingResistance(0.56↑) 및 RegenerationRate(1.04↑) 증가
├─ 시뮬레이션 틱(TickEcologySimulation) → 강화된 식생 Trait 기반 환경 회복 가속
├─ 먹이 부족 선택 압력 → 몬스터 제안/검증/커밋 → 2세대 몬스터 BodyScale(0.87↓) 및 RoamRadius/Speed 증가
└─ AsyncTask 기반 비동기 워커로 Game Thread 블로킹 없이 Proposal 안전 생성 및 커밋
```

이 흐름이 완전한 양방향 생태계 피드백 루프로 검증되었으며, 각 Dummy 부분을 실제 Mass 개체군 및 외부 LLM 서비스로 확장할 수 있습니다.

# 30. 마지막 원칙

이 문서의 목적은:

> **현재 구조를 영원히 고정하는 것**

이 아니다.

목적은:

> **왜 지금 이런 구조를 선택했는지 공유하고, 이후 팀원이 더 좋은 구조로 안전하게 발전시킬 수 있게 하는 것**

이다.

따라서 더 좋은 방법이 있다면 바꿔도 된다.

다만 다음 세 가지는 항상 확인한다.

```text
왜 바꾸는가?
어떤 책임이 이동하는가?
다른 파트와의 Contract를 깨뜨리는가?
```

그리고 중요한 구조 변경은 코드만 바꾸지 말고 이 문서와 관련 Architecture / Data Contract 문서도 함께 갱신한다.
