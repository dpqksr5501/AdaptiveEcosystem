# AdaptiveEcosystem — 진화 모델 확장 설계

## 결론
현재 구조는 **몬스터가 환경·플레이어 압력을 받아 세대 단위로 Trait이 변하는 적응형 진화 구조**는 갖고 있다.
하지만 식생은 아직 `VegetationDensity`, `FoodAvailability` 같은 **환경 입력값**일 뿐, 식생 자체의 세대별 Trait 진화는 없다.

따라서 목표 표현은:
> 자연선택의 압력 → 변이 → 검증 → 다음 세대 상속을 게임 시스템으로 추상화한 동적 생태계

라고 잡는 것이 정확하다.

## 현재 몬스터 진화 구조
```text
Environment + Player Pressure + Population + Generation + CurrentProfile
→ FEvolutionContext
→ LLM / Rule Provider
→ FEvolutionProposal (Trait Delta)
→ Validator
→ FSpeciesEvolutionProfile
→ 다음 세대 / 이후 Spawn에 적용
```

현재 몬스터 Trait:
- Phenotype: BodyScale, LegScale, BodyBoneScale, ColorBrightness, ColorTintStrength, MorphWeight
- Gameplay: MoveSpeedMultiplier, HealthMultiplier, AttackMultiplier
- Behavior: Fear, Aggression, GroupAffinity, HidePreference
- Ecology: MigrationTendency, RoamRadiusMultiplier, DayActivityPreference, NightActivityPreference

## 현재 부족한 점
현재 식생 관련 값:
```text
VegetationDensity
FoodAvailability
```
은 Region Environment State다.

즉:
```text
식생 상태 → 몬스터 진화 입력
```
은 되지만,
```text
플레이어/몬스터 압력 → 식생 Trait 변화 → 다음 세대 식생
```
은 아직 없다.

또한 현재 `Generation += 1`은 게임 규칙상의 세대 증가이며 실제 번식/유전 개체군 시뮬레이션은 아니다.

## 목표 구조
```text
Player / Environment / Ecology Pressure
          ↓
     Ecology State
      ↙       ↘
Monster      Vegetation
Context       Context
  ↓             ↓
LLM/Rule      LLM/Rule
  ↓             ↓
Trait Delta   Trait Delta
      ↘       ↙
        Validator
      ↙       ↘
Monster      Vegetation
Profile       Profile
      ↘       ↙
     다음 생태 사이클
```

몬스터와 식생이 서로 직접 수정하지 않고, 공통 Ecology State를 통해 영향을 주고받는다.

## 식생 진화용 최소 Trait
초기 MVP는 3개만 권장:
```text
GrowthRate
RegenerationRate
GrazingResistance
```

예시 구조:
```cpp
USTRUCT(BlueprintType)
struct FVegetationTraits
{
    GENERATED_BODY();

    float GrowthRate = 1.0f;
    float RegenerationRate = 1.0f;
    float GrazingResistance = 0.5f;
};
```

## 식생 Evolution Profile
```text
RegionId
VegetationSpeciesId
Generation
ProfileRevision
Traits
```

예:
```text
Forest_A × Grass_A
Forest_A × BerryBush_A
```

몬스터와 식생 Trait 의미가 다르므로 초기에는 별도 Profile 타입을 권장한다.

## 식생 Evolution Context
최소 입력:
```text
WorldEpoch
ContextRevision
RegionId
VegetationSpeciesId
Environment
HarvestPressure
GrazingPressure
Generation
CurrentProfile
```

MVP에서는:
```text
Rainfall
VegetationDensity
FoodAvailability
HarvestPressure
GrazingPressure
CurrentProfile
```
정도면 충분하다.

## 식생 Evolution Proposal
LLM은 절대값이 아니라 Delta를 제안한다.

```text
GrowthRateDelta
RegenerationRateDelta
GrazingResistanceDelta
```

예:
```json
{
  "growth_rate_delta": -0.02,
  "regeneration_rate_delta": 0.04,
  "grazing_resistance_delta": 0.06
}
```

## 자연선택처럼 보이게 만드는 3요소

### 1. Selection Pressure
환경과 플레이어/생태 행동이 방향성을 만든다.
```text
사냥 압력↑ → 빠른 이동/높은 경계 성향이 유리
초식 압력↑ → 재생속도/섭식 저항성이 높은 식생이 유리
강우량↓ → 건조 저항성이 높은 식생이 유리
```

### 2. Variation
LLM 또는 Rule Provider가 작은 Trait Delta를 제안한다.

### 3. Inheritance / Generation
승인된 Profile을 다음 세대나 새 Spawn이 상속한다.

## 중요한 세대 규칙
```text
현재 살아 있는 개체는 생성 당시 Profile을 유지한다.
Species Profile이 갱신되어도 기존 개체 즉시 변화 X.
새로운 세대 / 새 Logical Agent / 새 Spawn에 갱신 Profile 적용.
Mass Representation 전환은 새 세대가 아니다.
같은 StableAgent는 기존 ProfileRevision 유지.
```

## 몬스터 ↔ 식생 피드백 예시
```text
Wolf 사냥 증가
→ Wolf Population 감소
→ Deer 생존률 증가
→ 초식 압력 증가
→ Vegetation Density 감소
→ Food Availability 감소
→ 몬스터 Evolution Context 변화
→ 식생도 Regeneration/GrazingResistance 방향으로 적응
→ 다음 생태 사이클
```

## LLM의 역할
LLM의 질문:
> 현재 환경과 누적 압력을 고려했을 때, 허용된 Trait 공간 안에서 다음 세대가 어느 방향으로 얼마나 변하는 것이 자연스러운가?

LLM 금지:
```text
Actor 직접 수정
Population 직접 변경
Environment 직접 덮어쓰기
Validator 우회
새 Trait 임의 생성
```

## Validator
몬스터/식생 모두:
```text
Proposal
→ Schema/Revision Check
→ NaN/Inf Check
→ Max Delta Per Generation
→ Mutation Budget
→ Hard Limit
→ Commit
```

식생 초기 튜닝 예:
```text
GrowthRate          0.70 ~ 1.30
RegenerationRate    0.70 ~ 1.30
GrazingResistance   0.00 ~ 1.00
MaxDeltaPerGen      0.10
MutationBudget      0.20
```

## 첫 MVP
```text
Region: Forest_A

Monster: Wolf
- BodyScale
- MoveSpeed
- Fear
- Aggression

Vegetation: Grass_A
- GrowthRate
- RegenerationRate
- GrazingResistance
```

입력 예:
```text
Wolf HuntingPressure = 0.8
Grass GrazingPressure = 0.7
Rainfall = 0.2
```

Rule/Dummy Provider → Proposal → Validator → Generation/ProfileRevision 증가까지 먼저 검증한다.

## 구현 순서 및 현재 진행 현황
```text
[v] 1. 현재 Monster Evolution 구조 유지
[v] 2. Vegetation Trait/Profile 계약 추가 (FVegetationTraits, FVegetationEvolutionProfile)
[v] 3. Vegetation Context/Proposal 추가 (FVegetationEvolutionContext, FVegetationEvolutionProposal)
[v] 4. Vegetation Validator 추가 (UEvolutionValidator::ValidateAndApplyVegetationProposal)
[v] 5. Dummy/Rule Provider (UDummyEvolutionDecisionProvider::RequestVegetationProposal)
[v] 6. Forest_A × Grass_A Vertical Slice (UEcologyServerSubsystem 및 AEcologyBootstrapTestActor 검증)
[v] 7. Environment ↔ Vegetation 연결 (AEcologyRegion::ApplyVegetationRegrowth & UEcologyServerSubsystem::TickEcologySimulation)
[v] 8. Monster ↔ Vegetation Feedback 연결 (RecordGrazing -> GrazingPressure/FoodAvailability -> 몬스터 & 식생 동시 적응)
[v] 9. 비동기 의사결정 파이프라인 (AsyncTask 기반 GameThread 논블로킹 RequestProposalAsync / RequestVegetationProposalAsync)
```

## 변경 가능
Trait 종류, 범위, Pressure 종류, 세대 주기, Trigger, LLM Backend, Mutation Budget은 변경 가능하다.

다만 다음 경계는 유지 권장:
```text
환경/압력 → Context
AI → Proposal
Validator → Commit
다음 세대가 Profile 상속
Actor가 AI Output 직접 적용 X
```

## 발표 표현
권장:
> 플레이어 행동과 환경 변화가 선택 압력으로 누적되고, LLM이 허용된 Trait 공간에서 다음 세대의 적응 방향과 변화량을 제안합니다. 몬스터뿐 아니라 식생에도 같은 원리를 적용해 서로 영향을 주는 생태 피드백을 구현하려고 합니다.

더 정확히:
> 자연선택의 압력 → 변이 → 검증 → 세대 상속 과정을 게임 시스템으로 추상화한 구조입니다.
